### E2E 실행 중 발견해 고친 것 (2026-11-18)

- **할 일 카드 메뉴 클릭이 아래 카드로 새던 문제 (리팩토링 회귀)**: 카드 전체를 덮는 상세 버튼을 넣은 뒤, hover 시 `transform`이 쌓임 맥락을 만들어 열린 메뉴가 다음 카드 아래에 깔렸다. 그래서 "삭제하기"를 누르면 아래 카드의 상세가 열렸다. 메뉴가 열린 카드를 `has-[[role=menu]]:z-20`로 올려서 고쳤다. (`ListItem`, `TaskListCard`)
- **할 일을 수정해도 이전 이름이 보이던 문제 (기존 백엔드 경쟁 상태)**: 백엔드는 반복 일정의 그날 할 일을 조회할 때 만든다. 그래서 같은 날짜의 할 일 목록을 동시에 조회하면, 예를 들어 할 일 목록과 그룹 상세를 함께 조회하면, 같은 할 일이 두 개 생긴다. 수정은 한쪽에 적용되는데 목록은 다른 쪽을 보여 준다. API만으로 재현했다(8회 중 2회, 요청을 순서대로 보내면 12회 중 0회). 클라이언트에서는 `invalidateTaskQueries`가 할 일 목록을 먼저 다시 받은 뒤 나머지를 갱신하게 바꿨다. 다만 여러 사용자가 동시에 조회하는 경우는 **백엔드 수정이 필요**하다.
- E2E 설정: 같은 이유로 E2E를 `workers: 1`로 직렬 실행하고, 포트를 `E2E_PORT`로 바꿀 수 있게 했다. 스펙도 정리했다. 게시글의 `글쓰기` 링크는 정확히 일치할 때만 찾고, 할 일 삭제는 실제 할 일 카드가 사라졌는지로 검증한다. (이전에는 목록 링크 라벨을 확인해서 항상 통과했다)
- 로컬 E2E에는 `.env.local`에 `E2E_EMAIL`, `E2E_PASSWORD`, `E2E_TEAM_ID`가 필요하다. 팀에는 할 일 목록이 하나 이상 있어야 한다.

### 적용한 주요 구조 변경

- **인증**: `proxy.ts`(Next16 middleware)가 access 토큰을 미리 갱신, 보호 판단은 refresh 토큰 기준(`hasAuthSession`), RSC에서 쿠키 쓰기 실패를 무시하고 새 토큰으로 재시도, 로그인/로그아웃 시 Query 캐시 초기화, 로그인 리다이렉트 시 현재 경로 보존, OAuth state nonce 검증.
- **API 계층**: `src/apis/endpoints.ts`(경로 단일화) → `src/apis/<domain>/server.ts`(serverFetcher) / `index.ts`(공개 API, `publicFetcher`). 미사용 axios 래퍼 삭제. 실패는 `ApiError{status, body}`.
- **Server Action**: 모두 `src/actions/*.action.ts`로 이동, `runAction()`으로 `ActionResult<T>` 반환 + zod 입력 검증. 클라이언트는 `useActionMutation()`으로 사용. 전역 `MutationCache` 에러 토스트(`meta.silentError`로 끔).
- **조회**: Server Action 대신 RSC에서 미리 불러와 `HydrationBoundary`로 전달, 클라이언트 재조회는 BFF GET 라우트(`/api/proxy/*`, `/api/team-page/:id`). 쿼리 키는 `src/queries/queryKeys.ts` 하나로 통합.
- **공용 컴포넌트**: `Dropdown`/`DropdownSelect`(키보드·바깥 클릭·aria), `ConfirmModal`, `TaskListNameModal`, `CommentItem`, `Pagination`, `StatusPage`, `TeamAvatar`, `Button isLoading`, Modal 포커스 트랩, 모바일 드로어 `inert`.
- **이름 정리**: `components/sideBar` → `components/sidebar`, `[teamId]/_components/task-list` → `taskList`, 액션 파일명 통일.

### 하지 않은 것 / 남은 일

- **N3 (라우트 URL 통일)**: URL이 바뀌므로 팀 합의 후 진행.
- **C9**: 팀 카드 크기를 아직 `useMediaQuery`로 결정한다. (`Team` 컴포넌트를 반응형 클래스로 바꾸는 작업 필요)

- **B5**: 요청 수는 줄였지만(반복 일정은 추가 요청 없이 목록 매칭, 동시성 6 제한) 근본 해결은 백엔드 기간 조회 API가 필요.

## 2. 현재 아키텍처 요약

### 인증

- 이메일 로그인: `loginAction`(Server Action)이 axios `signIn`을 호출한 뒤 `setAuthTokens`가 httpOnly 쿠키 2개를 저장한다(access 1h, refresh 14d).
- 카카오 로그인: Route Handler(`(auth)/oauth/kakao/*`)가 같은 쿠키를 저장한다.
- 라우트 보호: middleware/proxy 없이 `(p)/layout.tsx`의 `hasAuthTokens()`로만 판단한다.
- 토큰 갱신: `serverFetcher`가 401을 받으면 refresh한 뒤 한 번 재시도한다.

### 데이터 흐름 (경로가 세 가지로 섞여 있음)

1. 서버 컴포넌트에서 `apis/*/server.ts`(serverFetcher) 호출
2. 클라이언트 TanStack Query의 `queryFn`과 `mutationFn`에서 `'use server'` Action 호출 (조회에도 사용)
3. `clientFetcher`(axios, 인증 헤더 없음): 공개 API 전용인데 인증 필요 API용 래퍼도 다수 남아 있다(대부분 미사용).

- Hydration(`HydrationBoundary`)은 `tl/page.tsx` 한 곳에서만 쓴다.

### 문제의 뿌리 3가지

1. **Server Action 사용 방식이 통일되어 있지 않다.** 결과를 반환하는 Action과 예외를 던지는 Action이 섞여 있고, 조회에도 Action을 쓴다. 그래서 운영 빌드에서 에러 메시지가 사라지고, 요청이 직렬로 처리되며, 캐시와 Hydration을 활용하지 못한다.
2. **계층 경계가 무너져 있다.** `src/queries`, `src/hooks`, `src/components`가 `src/app/**/_actions`를 import한다. API 정의도 action, `apis/index`, `apis/server` 세 곳에 중복되어 있다.
3. **공용 컴포넌트가 충분하지 않다.** Dropdown, Modal, Button 로딩 상태, 아바타가 부족해서 각 화면이 같은 코드를 다시 구현하고, 그 과정에서 접근성이 빠진다.
